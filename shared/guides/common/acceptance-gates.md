# 交付验收门禁

本 guide 只定义项目级的验收路由和准入条件；跨语言、业务逻辑、并发、事务、幂等、授权、安全、索引和性能的具体检查分别由全局 `frontend-acceptance` 与 `backend-acceptance` skill 执行，不能在各 harness 中复制一份。

## 变更面判定

| 变更面 | 识别信号 | 交付前必须加载 |
|---|---|---|
| 后端 | handler/controller、service/application、repository/ORM、migration/SQL、鉴权、队列、worker、定时任务、外部调用、服务配置 | `backend-acceptance` |
| 前端 | `.vue`、`.ts/.tsx/.js`、路由、store、composable、API client、表单、浏览器安全、用户界面 | `frontend-acceptance` |
| 契约/联调 | DTO、OpenAPI/proto、错误码、分页、权限、数据库 schema、支付/消息状态或跨端类型 | 前后端两个 skill；后端先验收不变量，随后做联调 |
| 包/库 | 仅公共库、纯函数、类型或文档，没有服务入口、数据库、队列或用户流程 | 包专属测试、API 兼容性和供应链检查；默认不加载业务后端验收 |

目录名只是初筛。以实际运行行为和变更影响为准；一个提交同时触碰多个变更面时取并集。

## 验证层级

1. **开发验证**：项目规定的 build、lint、类型检查、单元/集成测试、架构传感器和必要的 `-race`。
2. **功能验收**：需求来源、调用链、状态转换、错误路径、权限、数据一致性、重复提交、失败恢复和关键用户流程。
3. **发布验收**：真实或等价环境的数据库/队列/支付/外部依赖、并发与容量、迁移回滚、监控、回滚和安全证据。

普通小改动可按影响面执行第 1 层；新增或修改运行行为在交付前至少执行第 2 层；涉及核心数据、权限、支付、库存、消息、跨服务或生产配置时执行第 3 层。

## 硬门禁

- 纯后端 harness：运行行为改动交付前必须加载 `backend-acceptance`。
- 纯前端 harness：用户界面或浏览器运行行为改动交付前必须加载 `frontend-acceptance`。
- 全栈 harness：后端、前端和契约变更必须分别加载对应 skill，并保留一份联调结果。
- 需求来源、关键不变量、权限、事务/幂等、关键流程或核心依赖不可验证时，结论只能是“未验证/不准入”，不能用 build、截图、mock 或单测替代。
- 文档、注释、纯格式或不改变运行行为的配置说明可跳过完整验收，但报告中要说明跳过理由。

## 交付报告最小字段

```text
范围：harness、commit、变更面、环境
开发验证：命令、版本、结果
验收 skill：frontend-acceptance / backend-acceptance / 两者
需求与不变量：已证实、未确认、未覆盖
关键失败路径：事务、幂等、并发、权限、外部依赖
安全/性能/数据：证据、预算、未验证项
阻断项：严重级别、复现、修复验收条件
结论：准入 / 有条件准入 / 不准入
```
