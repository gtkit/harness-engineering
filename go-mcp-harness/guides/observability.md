# MCP 可观测性与容量

## 日志

按 `.harness/guides/dependencies.md` 优先核实 gtkit/logger。stdio stdout 永远保留给协议；日志输出目标、启动/关闭与 SDK 错误适配都需验证。诊断日志不等于 MCP 协议 logging 功能，后者按所选版本与客户端能力启用。

结构化记录工具名、传输、业务结果类别、耗时、取消来源与提交状态；使用经过边界验证的请求关联标识。跨进程调用传播 trace 时遵循信任策略，不将用户提供的任意字段当服务端权限。

默认不记录完整参数、结果、文件绝对路径、token、Authorization、cookie、会话凭据或敏感下游响应。脱敏在序列化和落盘前完成；指标也不使用这些字段。日志失败与收尾不应导致无限阻塞。

## 指标与告警

根据实际部署需要记录：调用/失败/取消次数与延迟、在途请求、排队/拒绝、活动流、流写失败、下游耗时、处理字节/文件数、提交后清理失败。工具名可以作为有界维度；用户、请求 ID、路径不能直接成为无限基数 label。

HTTP access log 的成功状态不能代替工具结果成功。协议拒绝、认证拒绝、工具业务错误和基础设施失败分别观察。没有 metrics 平台的小型本地插件不因此引入监控服务器。

## 容量与性能证据

先记录输入和目标：并发客户端、峰值调用率、P95/P99、输入/输出上限、耗时分布、内存/磁盘预算和下游限制。没有用户数据就标为待测，不伪造通用 QPS。

可用 `在途调用 ≈ 调用率 × 平均执行时间` 估算起点，再以代表性实测校准。长流数量、短请求数量、CPU 工作和外部进程有不同限制；限流、并发、队列与字节上限分别配置。

性能优化先测基线，再定位瓶颈、做最小修改、同环境重复比较延迟/吞吐/分配/资源，存在可复核收益才保留。测试数据形状、工具版本、失败/超时样本和波动一起记录，禁止仅展示最快样本。
