# Go MCP 架构与装配

## 定位与实施前事实

MCP 服务可以是客户端拉起的本地进程，也可以是常驻 HTTP 服务；插件清单和包管理器只是分发入口。先记录项目真实文件、启动方式、SDK/Go/协议版本、目标客户端、授权来源、外部依赖和已有测试，再按现有目录实现。

只需要 stdio 的项目不顺带开放端口；只需要 HTTP 的项目不强制引入 Node 启动器。明确同时支持时才共享业务实现并分别装配传输。两种传输的凭据来源、执行身份和资源范围必须分别定义。

## 职责边界（不等于目录模板）

| 职责 | 持有内容 | 约束 |
|---|---|---|
| 入口装配 | 配置、信号、依赖创建、传输、关闭顺序 | 生命周期由入口拥有，失败时释放已创建资源 |
| MCP 适配 | schema、参数转换、上下文、结果/错误映射 | 校验后调用业务，不套 REST 响应信封 |
| 业务操作 | 权限、不变量、提交点、重复调用策略 | 不依赖具体 HTTP 请求或 stdio 全局状态 |
| 外部能力 | 文件、子进程、数据库、HTTP API | 接收 context；资源有所有者，失败可分类 |

小项目允许这些职责位于同一 `internal` 包；只有真实重复或可验证的替换需求才增加接口。不要为每个工具发明一套 repository/service/manager 链。

## 兼容与生命周期

- 保留工具名、参数必填性、默认值、结果形状、资源标识和客户端启动命令；先列出外部调用方再评估改动。
- transport 层提供经验证的主体，业务层仍检查主体对具体资源的权限。不得把某次请求的凭据存入进程全局变量。
- 请求、传输连接、服务进程和持久任务是不同生命周期。按协议版本定义断连/取消；只有明确持久任务契约才允许工作跨越请求结束。
- 停止接新请求、取消/限时等待在途工作、释放依赖、限时刷新日志；分别处理关闭失败，不能覆盖原始业务错误。
- 工具描述与执行能力一致。尚未实现的工具明确不可用，不能返回看似成功的占位结果。

## 配置契约

先核对项目实际配置来源和优先级；不凭 harness 设定新的运行字段。新增字段必须同时说明用途、作用范围、默认/留空回落、合法范围、冲突组合和示例。非法启动配置在开始接收请求前拒绝。

至少按所选模式说明：传输选择、授权资源、下游依赖、执行预算与并发；HTTP 另说明监听端点、认证/Origin、TLS 终止、代理和流超时。秘密由私有配置或密钥系统提供；测试/文档使用占位符。
