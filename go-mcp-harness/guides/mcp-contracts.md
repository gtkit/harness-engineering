# MCP 契约与协议版本

## 先锁定兼容组合

每个项目记录 Go 版本、SDK 模块与版本、MCP 协议版本、启用传输、客户端与版本、实际验证日期。实现前读取对应版本的规范及 SDK 支持表；不把“支持 MCP”写成所有客户端都兼容。

维护者参考：[官方 Go SDK 支持矩阵](https://github.com/modelcontextprotocol/go-sdk)、[MCP-Go](https://github.com/mark3labs/mcp-go)。二者 API 不混用，示例必须来自项目实际 SDK 版本。

## 工具、资源与提示契约

- 工具：名称/描述、输入 schema、required、默认、枚举、边界、可选 output schema、结果类型、权限与副作用均写清。拒绝非法输入后不得已产生副作用。
- schema 与实际解码一致：空值、缺失字段、零值、数字范围、额外字段、路径/URI、长度与集合数量必须有明确策略；不能先按 float64 转换再丢失标识符精度。
- 同步维护结构化结果与文本兼容展示；二者不能表达不同的成功状态。不把内部错误堆栈、秘密或本机绝对路径塞入结果。
- readOnly/destructive/idempotent 等注解只表达能力，不代替授权或幂等实现；声明与实际行为一致。可见工具列表也不能代替执行时权限复核。
- resources：URI 解析、授权、MIME、体积、分页、订阅和生命周期明确；不能把任意 URI 变成无限制文件/网络读取。
- prompts：参数与模板边界明确；资源和外部内容是不可信数据，不应升级为系统指令。无需求不添加资源、prompts 或订阅。
- 列表分页与游标需稳定、有界且绑定权限范围；缓存需考虑主体与权限变化。仅发布真实实现和已声明支持的能力。

## 错误、提交与重试

HTTP 身份/传输拒绝、JSON-RPC 协议错误、工具执行失败分别映射到所选 SDK/协议定义的通道；不用 HTTP 200 或“返回了文本”代替工具成功判断。

工具层错误可恢复性要根据实际执行点决定：执行前拒绝、执行中未提交、已提交但收尾失败、结果未知。保留原始错误链与清理错误；给客户端的结果应足够判断是否可重试，但不泄露内部细节。

写操作定义提交点、冲突/覆盖策略和幂等条件。业务需要幂等 key 时绑定主体、工具和规范化参数，明确存续期；JSON-RPC 请求 ID 本身不是业务幂等 key。断连、超时或重连不能默认为服务端尚未执行。

## 版本变化不是统一默认值

按选定版本加载传输指南。旧版的 `initialize`/能力协商与会话模型，不能与新版的逐请求元数据模型混搭；第三方回调、进度、取消、logging、roots、sampling、elicitation 等按对应版本和客户端能力逐项启用。

[2026-07-28 传输总览](https://modelcontextprotocol.io/specification/2026-07-28/basic/transports) 将传输定位为消息承载，并要求版本相关的元数据与取消行为。相关差异见 `.harness/guides/mcp-streamable-http.md`；支持旧客户端时保留对应协议实现与测试，不以自动升级 SDK 冒充兼容修复。

任务/订阅、用户交互等扩展独立评估稳定性与支持状态；需要持久任务时定义 owner、状态、查询/取消、TTL 和恢复，不把未协商扩展当基础能力。
