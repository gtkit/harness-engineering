# TypeScript MCP 架构

## 先核对事实

从真实入口、package scripts、锁文件和客户端配置确认：服务由 TypeScript 实现，使用的运行时/SDK/协议版本、stdio 或 Streamable HTTP、是否通过 npm 分发、访问哪些资源及写入权限。没有证据的能力标为未确认，不按安装命令推测实现语言。

本包不使用 Go。Go 服务加 npm launcher 是独立的 `go-mcp-harness` 场景；不得在本项目增加 Go helper、Go module 或 Go CI 来补齐 TS 功能。

## 保留结构，明确职责

保留现有目录和公开接口。入口负责配置、依赖装配与退出；SDK 适配层负责协议输入/输出；业务逻辑负责权限、操作和提交；文件/网络等资源由实际使用方管理。职责可在现有文件表达，不为套层次新增接口、容器或框架。

双传输时复用工具 schema、业务结果和副作用规则，身份来源与连接管理分别处理。只需要一种传输时不强制实现另一种。npm 安装/启动与 MCP 工具业务分开，不在 launcher 重复实现业务。

## 运行约束

- 配置在启动边界解析/校验；请求不能修改全局租户、token、目录或默认权限。
- 为任务、监听器、timer、流、子进程和外部连接明确 owner、取消信号和收尾预算，避免模块导入即产生不可控副作用。
- 不因有 HTTP 就引入 Express/Fastify、数据库、Redis 或复杂分层；仅复用项目实际需要的能力。
- 新配置同时更新默认/留空回落、约束、示例与说明；秘密来自用户私有配置或环境，不能写入仓库。

设计记录包含信任边界、工具提交点、外部副作用、版本组合、容量输入、失败/回滚与验收矩阵。小改动可简洁，但不能省略兼容与失败处理。
